# دليل التشغيل — معرض رقية (عليها السلام)

دليل عملي لمن يشغّل الموقع: البيئات، الاختبارات، ترحيل قاعدة البيانات، النسخ الاحتياطي، والطوارئ.
الأوامر بالإنجليزية كما تُكتب في الطرفية.

## 1. البيئات

| البيئة | قاعدة البيانات | تُستخدم لـ |
|---|---|---|
| **production** | مشروع Supabase `ruqayya-silver` (`hnkjmthvgfknwdnehegr`) | الموقع الحقيقي والزبائن الحقيقيون. لا يُغيَّر إلا بموافقة صريحة. |
| **staging** | مشروع Supabase `ruqayya-silver-staging` (`rlivlqddrzdrmfqeqnox`)، خطة مجانية | تجربة الترحيلات والدوال قبل الإنتاج. بيانات تجريبية فقط. |
| **local** | قاعدة PostgreSQL مؤقتة على جهاز المطوّر + PostgREST حقيقي | الاختبارات الآلية. تُنشأ وتُحذف تلقائياً. |

يختار الموقع البيئة من `assets/js/config.js`:
- `?backend=local` أو `?backend=staging` أو `?backend=production` في الرابط (تُحفظ لهذا التبويب فقط).
- نسخ المعاينة على Cloudflare Pages (`*.pages.dev` غير نطاق الإنتاج) ← staging تلقائياً.
- غير ذلك ← production.

## 2. الاختبارات الآلية

المتطلبات: PostgreSQL 16+، Python 3.11+، Chrome، PostgREST 12، Deno 2.

```bash
pip install -r tests/requirements.txt
export RQ_POSTGREST=/path/to/postgrest      # https://github.com/PostgREST/postgrest/releases (v12.2.3)
scripts/test.sh            # كل شيء
scripts/test.sh db         # قاعدة البيانات فقط (الترحيلات، الصلاحيات، الطلبات، المخزون)
scripts/test.sh e2e        # الموقع ولوحة التحكم في متصفح حقيقي
```

- `tests/db/` — تبني قاعدة جديدة لكل اختبار من `supabase/tests/stub.sql` (بديل محلي لأدوار Supabase وجداول auth/storage وصلاحياتها الافتراضية كما على الإنتاج) ثم كل ملفات `supabase/migrations/`.
- `tests/e2e/stack.py` — يشغّل الموقع كما هو + PostgREST حقيقي + بوابة محلية تحاكي Supabase (`/rest/v1`, `/auth/v1` مع MFA, `/storage/v1`, `/functions/v1`). لتجربته يدوياً:
  ```bash
  python3 tests/e2e/stack.py
  # الموقع:  http://127.0.0.1:8765/?backend=local
  # اللوحة:  http://127.0.0.1:8765/admin/?backend=local   (admin@test.invalid / local-admin-pass-123)
  ```
- كل البيانات في الاختبارات مصطنعة. لا تُستخدم بيانات زبائن حقيقيين أبداً.
- GitHub Actions يشغّل نفس الاختبارات عند كل push (`.github/workflows/test.yml`).

## 3. ترحيلات قاعدة البيانات

- الملفات: `supabase/migrations/NNNN_name.sql`، ولكل ترحيل بعد الأساس ملف تراجع `supabase/rollbacks/NNNN_name.down.sql`.
- `0000_baseline.sql` = مخطط الإنتاج الحالي كما هو (أُعيد بناؤه باستعلامات قراءة فقط). **لا يُطبَّق على الإنتاج** لأنه موجود فيه أصلاً.
- الاختبار `tests/db/test_migrations.py` يتحقق أن كل ترحيل: up ← down ← up يعيد المخطط نفسه حرفياً (بمقارنة pg_dump)، وأن التراجع ينجح وفي القاعدة بيانات.

### تطبيق ترحيل على staging ثم الإنتاج
1. كل الاختبارات المحلية خضراء.
2. على staging (أول مرة فقط): `supabase/staging/bootstrap.sql` ← `0000_baseline.sql` ← `supabase/staging/seed.sql`.
3. طبّق الترحيل الجديد على staging (SQL Editor أو `supabase db push` مرتبطاً بمشروع staging)، ثم جرّب الموقع على staging.
4. **الإنتاج — يحتاج موافقة صريحة من المالك:**
   - خذ نسخة احتياطية أولاً (القسم 5).
   - طبّق الترحيل في SQL Editor لمشروع الإنتاج في وقت هادئ.
   - شغّل استعلامات التحقق المكتوبة في رأس ملف الترحيل.
   - إن ظهرت مشكلة: شغّل ملف التراجع المقابل من `supabase/rollbacks/`.

## 5. الطلبات والمخزون (المرحلة 1)

- `place_order` يحجز المخزون داخل نفس العملية التي تُنشئ الطلب: آخر قطعة لا تُباع مرتين مهما ضغط الزبائن معاً.
- كل نموذج طلب يحمل مفتاحاً عشوائياً (`p_idempotency_key`)؛ إعادة الإرسال (ضغطتان، انقطاع إنترنت) تعيد **نفس** الطلب.
- إلغاء الطلب من اللوحة يعيد قطعه للمخزون، وإرجاعه من الإلغاء يحجزها من جديد (ويرفض إن بيعت لغيره)، وحذف طلب محجوز يعيد قطعه.
- سجل كل حركة: جدول `stock_movements` (للمدير فقط):
  ```sql
  select m.created_at, p.name, m.delta, m.reason, m.order_no from stock_movements m join products p on p.id = m.product_id order by m.created_at desc limit 50;
  ```
- المنتج بلا كمية (`stock` فارغ) = غير محدود ولا يُحجز.

## 6. الحماية من السبام والإغراق (المرحلة 2)

ثلاث طبقات:
1. **Cloudflare Turnstile** (في الدوال `submit-order` و`submit-inquiry`): خفي للزبون الحقيقي، يظهر مربع فقط عند الاشتباه.
2. **حقل مصيدة (honeypot)** مخفي في النموذجين: الروبوت الذي يملؤه يُرفض.
3. **حدود في قاعدة البيانات** تسري على كل الطرق (حتى الاتصال المباشر بالـ API):

| النوع | النطاق | الحد |
|---|---|---|
| طلب | نفس العنوان IP | ٦ / ١٠ دقائق، ٣٠ / يوم |
| طلب | نفس رقم الهاتف | ٤ / ١٠ دقائق، ١٢ / يوم |
| طلب | المتجر كله (قاطع طوارئ) | ٣٠٠ / ١٠ دقائق |
| رسالة | نفس العنوان IP | ٥ / ١٠ دقائق، ٣٠ / يوم |
| رسالة | الكل | ٢٠٠ / ١٠ دقائق |

تُخزَّن بصمات (sha256) فقط، لا عناوين ولا أرقام. تعديل حد:
```sql
update private.rate_rules set max_count = 10 where kind = 'order' and scope = 'ip' and window_seconds = 600;
```

**التفعيل على الإنتاج (بانتظار موافقة):** إنشاء مفاتيح Turnstile في Cloudflare ← سرّ `TURNSTILE_SECRET` في دوال Supabase ← نشر الدوال ← وضع مفتاح الموقع في `config.js` (`turnstile`) وتغيير `gateway` إلى `"edge"`. الموقع يرجع تلقائياً للطريق القديم إن لم تكن الدوال منشورة، فترتيب النشر آمن.

## 7. إشعارات تيليجرام (المرحلة 3)

- الطلب/الرسالة يُرسَل فوراً من الدالة؛ وإن فشل (تيليجرام معطل، انقطاع) يعيد `notify-retry` المحاولة كل دقيقة (pg_cron) بتباعد ١، ٢، ٤… دقائق حتى ساعة، لمدة ٣ أيام. لا يضيع أي إشعار (قد يتكرر نادراً).
- حالة الإشعار تظهر داخل الطلب في اللوحة. مفاتيح التشغيل/الإيقاف: «التواصل والمتجر ← إشعارات تيليجرام»، مع زر «إرسال رسالة تجريبية».
- **الإعداد (مرة واحدة، بانتظار موافقة):**
  1. أنشئ بوتاً عبر @BotFather واحفظ التوكن. أرسل أي رسالة للبوت، ثم افتح `https://api.telegram.org/bot<TOKEN>/getUpdates` لمعرفة `chat.id`.
  2. أسرار الدوال (Supabase ← Edge Functions ← Secrets): `TELEGRAM_BOT_TOKEN`، `TELEGRAM_CHAT_ID`، `CRON_SECRET` (عشوائي: `openssl rand -hex 24`).
  3. شغّل `supabase/scheduled/notify_cron.sql` في SQL Editor بعد استبدال `<PROJECT_REF>` و`<CRON_SECRET>`.
- فحص المعلّق:
  ```sql
  select order_no, created_at, notify_attempts, notify_error from orders where notified_at is null order by created_at desc;
  ```

## 8. الدوال (Edge Functions)

| الدالة | من يستدعيها | verify_jwt |
|---|---|---|
| `submit-order` | الموقع | false (تتحقق بنفسها: Turnstile + الأصل + حدود القاعدة) |
| `submit-inquiry` | الموقع | false |
| `notify-retry` | pg_cron (ترويسة `x-cron-secret`) | false |
| `notify-test` | لوحة التحكم (المدير فقط، تتحقق عبر `am_i_admin`) | false |
| `health` | مراقبة التوفر | false |

الأسرار: `SB_SECRET_KEY` (مفتاح `sb_secret_…`؛ إن لم يوجد تُستخدم `SUPABASE_SERVICE_ROLE_KEY` التلقائية)، `SB_PUBLISHABLE_KEY`، `TURNSTILE_SECRET`، `ALLOWED_ORIGINS` (نطاقات الموقع مفصولة بفواصل)، `TELEGRAM_BOT_TOKEN`، `TELEGRAM_CHAT_ID`، `CRON_SECRET`.

نشر (بعد موافقة): `supabase functions deploy submit-order --no-verify-jwt` (وكذا البقية) مع `--project-ref`.

## 9. لوحة التحكم: التحقق بخطوتين ورؤوس الأمان (المرحلة 4)

- بعد الترحيل `0005` لا تكفي كلمة المرور: قاعدة البيانات نفسها ترفض أي تعديل أو قراءة للطلبات أو رفع صور ما لم تكن الجلسة `aal2` (كلمة مرور + رمز تطبيق المصادقة).
- أول دخول بعد التفعيل: تظهر شاشة «تفعيل التحقق بخطوتين» مع رمز QR ومفتاح يدوي؛ امسحه بـ Google Authenticator أو Microsoft Authenticator واكتب الرقم. بعدها يُطلب الرقم عند كل دخول.
- خروج تلقائي بعد ٣٠ دقيقة بلا نشاط، ورسالة واضحة عند انتهاء الجلسة.
- **فقدت الهاتف؟** في SQL Editor:
  ```sql
  update private.admin_policy set require_mfa = false;   -- مؤقتاً
  ```
  ثم Supabase ← Authentication ← Users ← المستخدم ← احذف عامل MFA، ادخل وفعّل من جديد، ثم أعدها `true`.
- سياسة أمان المحتوى (CSP) في رأس `index.html` و`admin/index.html`: لا سكربتات مضمّنة، ولا سكربتات إلا من الموقع نفسه (و Cloudflare Turnstile للمتجر). الكود الذي كان مضمّناً انتقل إلى `assets/js/boot.js`.
- اللوحة ترفض العمل داخل إطار (iframe) لمنع الخداع بالنقر؛ على Cloudflare Pages تُضاف رؤوس `X-Frame-Options` و`frame-ancestors` من `_headers`.
- صلاحيات API: لا `TRUNCATE`/`TRIGGER`/`REFERENCES` لأدوار الواجهة على أي جدول (`0004`). اختبار آلي يمنع ظهور أي دالة جديدة متاحة للزوار دون قصد.

**إعدادات Supabase Auth (يدوياً، بانتظار موافقة):** إيقاف التسجيل العام (Authentication ← Providers ← Email ← Allow new users to sign up = off)، تفعيل Leaked password protection، أقل طول لكلمة المرور ١٢، وبريد SMTP خاص للرسائل.

## 10. المراقبة والتعافي من الأخطاء (المرحلة 5)

- المتجر يعيد محاولة جلب البيانات تلقائياً (٤ محاولات بتباعد)، ويعرض آخر نسخة محفوظة في المتصفح إن وُجدت؛ وإن لم توجد يظهر تنبيه هادئ مع زر «إعادة المحاولة» ويعيد المحاولة تلقائياً عند عودة الإنترنت.
- أخطاء JavaScript في متصفحات الزوار تُسجَّل (بلا بيانات شخصية، ٢٠ لكل جهاز/١٠ دقائق) في `private.client_errors`؛ ملخصها للمدير:
  ```sql
  select public.client_error_summary();   -- من جلسة المدير، أو: select * from private.client_errors order by created_at desc limit 20;
  ```
- **مراقبة التوفر (بانتظار إنشاء حساب مجاني):** UptimeRobot أو Better Stack، فحص كل ٥ دقائق لـ:
  1. صفحة المتجر الرئيسية (نص متوقع: «معرض رقية»).
  2. `https://<PROJECT_REF>.supabase.co/functions/v1/health` (يرجع `200` و`"ok":true` حين تجيب قاعدة البيانات، و`503` غير ذلك).
  مع تنبيه على البريد/تيليجرام.
- ملاحظة الخطة المجانية: مشروع Supabase المجاني يتوقف بعد أسبوع بلا نشاط؛ مراقبة التوفر نفسها تبقيه نشطاً، والترقية لـ Pro تزيل القيد.

## 11. النسخ الاحتياطي والاستعادة

- **تلقائي (بانتظار تفعيل):** `.github/workflows/backup.yml` كل ليلة: `pg_dump` لمخططات المتجر ← تشفير بـ age بمفتاح المالك العام ← حفظ ٣٠ يوماً في GitHub (+ نسخة خارجية اختيارية على Cloudflare R2). لا يُخزَّن أي ملف غير مشفّر.
  - التفعيل: أنشئ مفتاحاً على جهازك `age-keygen -o ruqayya-backup-key.txt` (احفظه في مكان آمن خارج الإنترنت!)، ثم في GitHub ← Settings ← Secrets: `SUPABASE_DB_URL`، `AGE_RECIPIENT` (السطر `public key: age1…`)، وفي Variables: `BACKUP_ENABLED=true`.
- يدوي: `SUPABASE_DB_URL=… AGE_RECIPIENT=age1… scripts/backup.sh backups/`
- **تمرين الاستعادة (مُختبر آلياً):** `scripts/restore-drill.sh backups/ruqayya-….dump.age ruqayya-backup-key.txt` — يبني قاعدة مؤقتة من الترحيلات ويستعيد البيانات ويطبع الأعداد والفحوص. لا يلمس أي قاعدة حية.
- **استعادة كارثية إلى مشروع جديد:** `staging/bootstrap.sql` ← كل الترحيلات ← `scripts/restore-drill.sh ملف مفتاح "<رابط قاعدة المشروع الجديد>"` ← أنشئ مستخدم المدير في Auth ← `insert into public.admins select id from auth.users where email = '…';` ← ارفع صور المنتجات من نسخة التخزين.
- الصور والفيديو في Storage ليست ضمن نسخة قاعدة البيانات؛ نسخ Supabase اليومية (خطة Pro) أو تنزيل الحاوية `media` دورياً يغطيها.
- خطة Pro تضيف نسخاً يومية تلقائية لسبعة أيام (PITR اختياري مدفوع).

## 12. الكتالوج والبحث (المرحلة 6 — `0006`)

- حتى ٦٠ منتجاً: الموقع يحمّل الكتالوج كله مرة واحدة ويعمل كما كان تماماً. أكثر من ذلك: صفحات المتجر من الخادم (٢٤ منتجاً + «عرض المزيد»)، والبحث على الخادم، وصفحة المنتج وعناصر السلة تُجلب عند الحاجة.
- البحث يفهم العربية: أ/إ/آ = ا، ة = ه، ى = ي، بلا تشكيل، والأرقام العربية = الإنجليزية. نفس القواعد في المتصفح (`norm`) وفي قاعدة البيانات (`private.ar_norm`).
- اللوحة: الطلبات تُقرأ صفحة صفحة من `admin_orders` (بحث بالاسم/الهاتف/رقم الطلب + عدد كل حالة)، والأرقام من `admin_stats` (لا حدّ ٥٠٠ طلب بعد الآن).
- قياسات محلية: ٥٠٠٠ منتج — الرئيسية ٦ م.ث، صفحة عميقة ٨ م.ث، بحث ٤–٧٠ م.ث؛ ٢٠٠٠٠ طلب — قائمة اللوحة ٣٥–٤٥ م.ث، بحث بالهاتف ٤ م.ث.
- على Cloudflare: `/api/rpc/<دالة>` نسخة مخزّنة ٦٠ ثانية (البحث ٣٠)، وتبقى تخدم آخر نسخة سليمة حتى ٢٤ ساعة إن تعطلت قاعدة البيانات. تغيير سعر يظهر خلال دقيقة؛ الطلب نفسه يُحسب دائماً بالسعر الحالي في قاعدة البيانات.

## 13. الصور (المرحلة 7 — `0007`)

- كل صورة تُرفع من اللوحة تُحفظ بثلاثة مقاسات: `….v.webp` (حتى ١٨٠٠ بكسل) و`….v-1080.webp` و`….v-480.webp`. الهاتف لا ينزّل الصورة الكبيرة أبداً.
- الصورة يُعاد ترميزها دائماً في المتصفح: تُحذف بيانات الكاميرا والموقع الجغرافي (GPS) قبل الرفع.
- الصور القديمة (مقاس واحد) تعمل كما هي.
- «حسابي ← مساحة الصور»: يعرض الملفات التي لم يعد يستخدمها أي منتج/قسم/إعداد/طلب سابق (أقدم من ساعة على الأقل، والافتراضي يوم) ويحذفها بعد التأكيد.

## 14. الجداول القديمة (المرحلة 9 — `0008`)

## 16. اللغات: العربية · English · فارسی · اردو · Deutsch (`0010`)
- **كيف تُختار اللغة:** `?lang=ar|en|fa|ur|de` في الرابط، ثم آخر اختيار للزائر (محفوظ في متصفحه)، ثم لغة جهازه: إنجليزي أو فارسي أو أوردو أو ألماني، وإلا العربية. زر الكرة الأرضية في الشريط العلوي (على الهاتف يحلّ محلّ زر الوضع الداكن/الفاتح الذي ينتقل إلى القائمة)، وصف اللغات أعلى قائمة الهاتف، وروابط في أسفل كل صفحة.
- **الاتجاه:** العربية والفارسية والأوردو من اليمين، الإنجليزي والألماني من اليسار (`boot.js` يضبط `lang` و`dir` قبل ظهور الصفحة). الخطوط: الفارسية بخطوط العربية نفسها وبالأرقام الفارسية (۱۲۳)، الأوردو بخط النستعليق في العناوين، الإنجليزي والألماني بـ Cormorant Garamond وIBM Plex Sans.
- **النصوص العامة:** الترجمات الجاهزة في `assets/js/i18n.js`. أي نص يغيّره المالك بالعربية يظهر بالعربية في اللغات الأخرى حتى تُكتب ترجمته من «اللغات والترجمة» في اللوحة (تُحفظ في `settings.data.i18n.<lang>`) — لا يرى الزائر معلومة قديمة أبداً.
- **المنتجات والأقسام:** عمود `i18n` (اسم، وصف، حجر، معدن، شارة / اسم القسم ووصفه) من نافذة التعديل في اللوحة. الحقول الفارغة تظهر بالعربية، والأحجار والمعادن والشارات المعروفة تُترجم تلقائياً، والأوزان (١٢ غرام → 12 g).
- **ما يبقى بالعربية دائماً:** اللوحة، الطلبات المحفوظة (الدولة والمحافظة واسم المنتج تُرسل بالعربية مهما كانت لغة الزائر)، وإشعارات تيليجرام. رسالة واتساب التي يرسلها الزبون تكون بلغته.
- **التراجع:** `supabase/rollbacks/0010_translations.down.sql` (يحذف الترجمات المكتوبة للمنتجات والأقسام — صدّرها أولاً). الموقع يعمل بدون `0010`: المنتجات تظهر بالعربية والواجهة مترجمة.

## 17. زخرفة الواجهة: محراب ذهبي وورد أبيض
- **ما هي:** حول بطاقة الواجهة قوس محراب مدبّب بخطوط ذهبية رفيعة (خطان، وصف حبّات، ومقرنصات صغيرة)، نجمة ثمانية في تاجه مع وردة، وأغصان أرابيسك (إسليمي) تتسلّق جانبيه بأوراق خضراء وزهور بيضاء صغيرة، وباقتا ورد أبيض عند قدميه. خلفه شبكة نجوم ثمانية (گره) باهتة جداً، وبتلات تتساقط ببطء على جهة البطاقة. وغصن ورد عند زاوية صورة «من نحن». كله مرسوم بالكود (SVG) بلا صور.
- **الحركة:** بعد الافتتاحية يُرسم القوس بالذهب خلال ثلاث ثوانٍ، ثم تتفتح الورود، ويمرّ ضوء خفيف على القوس كل بضع ثوانٍ. من يطلب «تقليل الحركة» يراها كاملة ثابتة. تتوقف الحركة حين تكون الواجهة خارج الشاشة. تحلّ محلّ المدارات الدائرية خلف البطاقة.
- **أين:** الرسم في `assets/js/art.js` (`blooms`: `mihrab` و`feet` و`glint` و`girih`)، الأنماط في `site.css` (قسم «White roses»)، الإدراج في `heroBlooms()` في `site.js`. الصفحة الرئيسية فقط، وتنعكس تلقائياً في الإنجليزي والألماني.
- **التشغيل والإيقاف:** اللوحة ← الهوية والألوان ← «زخرفة الواجهة: محراب ذهبي وورد أبيض» (`theme.flowers`، مفعّلة افتراضياً).
- **الاختبار:** `tests/e2e/test_flowers.py` — يقارن صورة الصفحة بالزخرفة وبدونها ويتأكد أن أي سطر نص أو زر أو شارة لم يتغيّر بكسل واحد (عربي، إنجليزي، أوردو؛ هاتف ٣٦٠/٣٩٠، لوحي، حاسوب).
